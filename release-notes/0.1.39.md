UnraidClaw 0.1.39 makes a missing or refused Unraid API key obvious, and makes the settings page readable on Unraid's light themes. The CLI is unchanged apart from its version, and the OpenClaw plugin stays at 0.1.18 on npm.

## Security and reliability fixes

- Without an Unraid API key in **Settings > UnraidClaw**, every tool that reads through Unraid's GraphQL API failed with `GRAPHQL_ERROR: Invalid CSRF token`, because unraid-api falls back to session authentication when no key is sent. These routes now fail before contacting Unraid with HTTP 503 and `UNRAID_API_KEY_MISSING`, and the message says where to set the key ([#21](https://github.com/emaspa/unraidclaw/issues/21), thanks to @fct-sk for the report and diagnosis).
- A key Unraid refuses, for example one deleted from **Settings > Management Access**, is reported as HTTP 502 and `UNRAID_API_KEY_REJECTED` with Unraid's own message, such as `API key validation failed`. Other GraphQL failures keep `GRAPHQL_ERROR`.
- `/api/health` reports `unraidApiKeyConfigured` and checks the key with an authenticated query. It used to probe with a query unraid-api answers without a key, so a missing or refused key showed as `ok`. It now shows `degraded` with a `message` saying what to fix. See [API](https://github.com/emaspa/unraidclaw#api).
- The **Dashboard** and **Settings** tabs show the Unraid API key as **Not configured** when it is empty.

## Other changes

- The settings page is readable on the White and Azure themes. Its text and panel colours were written for a dark background, so most of the page showed light grey on light grey. On light themes they now follow the theme's own text colour, and destructive permissions stay red ([#20](https://github.com/emaspa/unraidclaw/pull/20), thanks to @stormshaker).
- The **Running**, **Configured** and **Active** status badges are now plain coloured text in Unraid's status colours on every theme, as native settings pages show a status.

## Upgrade notes

- Scripts and clients that match on `GRAPHQL_ERROR` for authentication failures should also handle `UNRAID_API_KEY_MISSING` (HTTP 503) and `UNRAID_API_KEY_REJECTED` (HTTP 502). Before this release the same failures came back as HTTP 400 with `GRAPHQL_ERROR`.
- Monitoring that reads `/api/health` may now see `degraded` on a server whose Unraid API key is missing or refused. That server's GraphQL-backed tools were already failing.
