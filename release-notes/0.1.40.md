UnraidClaw 0.1.40 fixes two problems found while checking UnraidClaw on Unraid 7.4.0: the VM list on servers with VMs disabled, and a false warning in container edits. Unraid 7.4.0 needs no other changes; its API's new GraphQL query limits and introspection policy do not affect UnraidClaw. The CLI is unchanged apart from its version, and the OpenClaw plugin stays at 0.1.18 on npm.

## Security and reliability fixes

- With VMs disabled in **Settings > VM Manager**, or the array stopped, Unraid's VM service (libvirt) is not running and `GET /api/vms` and `unraid_vm_list` failed with HTTP 400 `GRAPHQL_ERROR: Failed to retrieve VM domains: VMs are not available`. Both VM read routes now fail with HTTP 503 and `VMS_UNAVAILABLE`, and the message says how to start the service, so a stopped service is not taken for a server without VMs. See [VMs](https://github.com/emaspa/unraidclaw#vms).
- Unraid 7.4's API can return no VM list without an error. UnraidClaw answered that with HTTP 500; it is now an empty list.
- A container edit (`POST /api/template/:name/edit`, `unraid_template_edit`) checks that every mount of the running container is in the rebuilt command. Docker reports `/mnt/user/media` for a template path written as `/mnt/user/media/`, so a bind mount at such a path got a false "will no longer be mounted" warning. A named Docker volume at such a path was mounted a second time, which made `docker create` fail before the running container was touched. Trailing slashes no longer count.

## Upgrade notes

- Scripts and clients that read `/api/vms` should handle `VMS_UNAVAILABLE` (HTTP 503). Before this release the same condition came back as HTTP 400 with `GRAPHQL_ERROR`.
